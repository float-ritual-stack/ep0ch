# Datacore: what ep0ch can learn from a live query runtime

2026-10-30. Primary-source reading of Datacore's documentation and repository at [`1a83c5b` (2026-06-22)](https://github.com/blacksmithgu/datacore/tree/1a83c5b6ed95fe88179212b3867978af54cc00d9). I did not run Obsidian or benchmark the plugin. The [Obsidian community listing](https://community.obsidian.md/plugins/datacore) currently identifies 0.1.29 as the published version; the pinned source revision is later than that release and must not be assumed identical to its package.

## Finding

Datacore's useful move is to **separate selecting objects from presenting them**. Its index gives pages, sections, blocks, list items and tasks common identities and metadata. A small boolean query chooses a set; JavaScript/Preact then renders that set as a table, list, embed or custom component. A view subscribes to index updates, so it can retain local UI state while data changes. [Metadata model](https://blacksmithgu.github.io/datacore/data), [query reference](https://blacksmithgu.github.io/datacore/data/query), [JavaScript views](https://blacksmithgu.github.io/datacore/code-views).

That is a better seam than Dataview's display-shaped `TABLE … FROM … WHERE …` language for a programmable outline. It does **not** yet remove the author's query/code burden: Datacore's own quickstart says the non-JavaScript view path is unavailable, and its roadmap leaves field autocomplete, direct view filtering/sorting controls and inline editing unchecked. The source's stock `TableView` renders cells without an edit handler. Treat the advertised visual database UI as direction, not evidence of a shipped workflow. [Quickstart](https://blacksmithgu.github.io/datacore/quickstart), [roadmap](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/ROADMAP.md#views), [table source](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/src/api/ui/views/table.tsx#L228-L255).

## What is actually there

| Concern | Observed design | Lesson for ep0ch |
|---|---|---|
| Object model | Indexed objects have intrinsic `$` fields separate from open author fields; pages contain sections, blocks and nested list items/tasks. A `yaml:data` codeblock is an independently queryable object. Generic files are indexed, while rich image/video/PDF metadata remains on the roadmap. [Metadata](https://blacksmithgu.github.io/datacore/data), [blocks](https://blacksmithgu.github.io/datacore/data/blocks), [roadmap](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/ROADMAP.md#indexing) | A block already has a stable identity in ep0ch. Make authored properties, tasks, links and fragments discoverable through the service's existing record/query surfaces; do not create a parallel Markdown index. |
| Query | `@page`, `@block`, `#tag`, `exists(field)`, path and linked-object selections compose with `and`, `or`, `!`, `parentof()` and `childof()`. Field expressions run against candidates. [Queries](https://blacksmithgu.github.io/datacore/data/query) | Keep one service-owned membership answer. Graph relations and arbitrary field names are worthwhile additions when the current view grammar cannot express the intended experience. Make the query readable as a sentence/chips in UI; do not impose another display DSL. |
| Execution | Types, tags, links, folders and fields have separate indexes. The evaluator intersects indexed candidate sets before scanning expressions. A search returns objects, duration and a maximum result revision. [Store](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/src/index/datastore.ts#L22-L64), [query executor](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/src/index/storage/query-executor.ts#L152-L266), [search result](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/src/index/datastore.ts#L309-L335) | Expose completeness, timing and source/result revisions in an inspector. The user should be able to tell whether a blank view is empty, still loading, or broken. Do not transplant an in-memory index into clients. |
| Live view | `dc.useQuery()` subscribes to the broad index `update` event, debounces by default, reruns the query, then interns results by object ID/revision so Preact can retain DOM/component state. `dc.useMemo()` and `dc.useArray()` help with grouping and transformations. This is reactivity through a stable view interface, **not a fine-grained query dependency graph**. [Hook](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/src/ui/hooks.tsx#L15-L142), [views guide](https://blacksmithgu.github.io/datacore/code-views), [local API](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/src/api/local-api.tsx#L223-L230) | ep0ch's render scripts already record reads and refresh their output through the service. Keep that producer path, stable row IDs and the client's current selection/scroll position. Reuse the current change feed instead of adopting broad per-view rescans. |
| Reuse | Named codeblocks and vault JS/TS files can be loaded with `dc.require`; views can use built-in pageable `dc.Table`, `dc.List`, embeds, buttons and controls. [Sharing code](https://blacksmithgu.github.io/datacore/code-views#sharing-code), [table](https://blacksmithgu.github.io/datacore/code-views/table), [list](https://blacksmithgu.github.io/datacore/code-views/list) | The equivalent is ep0ch's named script fence/extension lookup and `view.*` primitives, drawn by the existing NoteSurface and Herdr client. A new view should be a shared primitive or a composition of them, not custom terminal UI. |
| Discoverability | The current quickstart starts with a JSX fence and manually declared columns. The roadmap marks field autocomplete and direct manipulation of view configuration incomplete; the source's codeblock registration supplies syntax highlighting. [Quickstart](https://blacksmithgu.github.io/datacore/quickstart), [roadmap](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/ROADMAP.md#views), [codeblock registration](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/src/main.ts#L25-L78) | This is where ep0ch can outperform it: completion from actual property facets, query words and linked relations while typing, the same choices in a visual editor, and one self-describing action surface for mouse, keys and agents. |

The project advertises **2–10×** query/render gains over Dataview, but the inspected docs/source do not establish a reproducible comparison for ep0ch. It uses workers for parsing and an IndexedDB `localforage` cache in the pinned source, despite the roadmap marking “file-based persistence” checked. This is a reason to test actual user-visible latency, not to copy its storage scheme or quote the multiplier as measured fact. [README](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/README.md), [importer](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/src/index/web-worker/importer.ts#L10-L22), [cache](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/src/index/persister.ts#L13-L48), [roadmap](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/ROADMAP.md#technical).

## The old Obsidian export and pie's prior art

I inspected the export at `/opt/float/bbs/inbox/evan/outlines` by counting files and fence forms, without copying any personal note into this repository. It has 10,448 Markdown files, 10,433 with YAML front matter, 97 `dataviewjs` fences, 3 `dataview` query fences, and no `datacore` fences. Ninety-five of the JS fences call the generated `_ep0ch/graph` adapter. The useful evidence is that the exported outline already has enough structured fields for Obsidian to query, while most of the Dataview use is a generated graph bridge rather than many hand-authored tables. An ep0ch collection should consume the canonical blocks and properties directly and let an export remain an export.

Pie has already chosen the destination. The live *Collections: one component for table, gallery, feed and board* capability (`a2456aa8-33e1-453e-8a65-7c137813aacb`) says a saved view note or `::view{}` block is the one VIEW record, with layout tabs over one Question, a `site.answer` producer, shared list primitive and ListView, facets-fed controls, `views.planWrite`/`binding.set`, and agent tools reading the same record. It explicitly rejects a second answer path or editor. Its prior-art section includes Kitty's gallery, user-land cards that regexed property chips, and earlier view/spec/agent designs. *Reorient here* (`63132a65-e443-422f-85a7-10e5a64b9869`) says to build an end-to-end experience in one brief and PR. *Prototypes before ep0ch* (`0be35f1c-2b63-4d40-8b0f-c60c1655a423`) records hundreds of earlier proofs and rules out another idea-validation MVP. These are live pie notes, read on 2026-10-30 with `ep0ch show --machine float-2 --ws pie <id>`.

## Security and the execution boundary

Datacore transpiles authored JS/TS/JSX and executes it with `new Function` in the Obsidian renderer. Its `dc` API exposes the Obsidian `app`, and imported scripts use the same evaluator. That is trusted local code with the user's application reach, not a sandbox. [Evaluator](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/src/utils/javascript.ts#L25-L44), [renderer](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/src/ui/javascript.tsx#L28-L42), [local API](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/src/api/local-api.tsx#L65-L72), [script imports](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/src/api/script-cache.ts#L99-L121).

For ep0ch, the nvim and Google Docs tests in [AGENTS.md](../../../../AGENTS.md#before-you-build) are the intended policy: authored code and an owner's agents may perform the owner's actions; no content-based permission prompts or inspection of client names/notes. Preserve the mechanics that make these actions comprehensible and reversible: one action path, actor attribution, revisions, draft preservation, undo and no stolen cursor/focus. The current host script surface already offers `q`, `read`, `resolve`, `act`, agent `tools.*` and shared `view.*` through QuickJS. Every operation in the proposed collection experience must be callable by agents as well as by the person; actor differences affect attribution and cursor ownership, not capability. [Script surface](../scripts.md#globals), [effects and attribution](../scripts.md#effects-access-and-attribution), [door action architecture](../../../door/docs/UI-GRAMMAR.md#before-adding-a-feature). This paragraph is an ep0ch design inference, not a Datacore claim.

## Big swing: make the accepted collections capability feel alive

**Experience sentence:** Evan opens one collection note, asks for the notes related to a subject, reshapes the result through the accepted table/gallery/feed/board presentations, edits source properties in place, and gives an agent the same controls. The collection updates while he works; opening a row follows the existing tile's open rule. One coherent spike should carry the authoring, reading, editing and agent path together. This is a design proposal based on the sources above and ep0ch's accepted collections direction, not existing Datacore behavior. It should extend that capability's owner rather than create another kind of collection, query declaration or projection slot.

1. **Author where the result lives.** Use the accepted collection note/form and the existing saved-view query grammar with open property names. Completion after its query/column/group words offers real field facets and relation operators from the service. A picker can change the same canonical source without creating a second query model. The raw form remains readable to an agent and editable by the person.
2. **Render through shared parts.** The service returns membership, facets, complete/error state and stable block records. The accepted collection presentation uses the existing projection path and component primitives. NoteSurface draws it in the door; Herdr Detail draws that same projection. A query tile may show it, while the existing service and reader keep ownership of meaning and rendering. [Existing script view builders](../scripts.md#view), [reuse map](../../../door/docs/UI-GRAMMAR.md#before-adding-a-feature).
3. **Make it a working surface.** Click or key into a cell using the existing ElementEdit/DraftSession editor; `act` exposes the same action and arguments. Writes use the service's property patch and `views.planWrite`, with revision checks and undo. A row that stops matching disappears for a stated reason, and a failed write keeps the text in the editor. A calculated column may come from a named render script, so a user can grow from a table into a custom live view without changing models. [Element editing reuse](../../../door/docs/UI-GRAMMAR.md#before-adding-a-feature), [existing write owner](../../CONTRIBUTING.md#source-boundaries).
4. **Make the part describe itself.** In the collection, a visible source/inspector shows the query, each field's origin, row count, completeness, last refresh and timing. The power bar offers “make a collection”, query and view actions; `actions --doc` and agent tools read the same definitions. An agent can create, adjust, inspect, use and undo the collection without the person's focus moving. [Action design](../../../door/docs/UI-GRAMMAR.md#before-adding-a-feature), [completion-source contract](../extensions/README.md#completion-sources-rows-where-a-person-types).
5. **Prove the whole loop once.** On a fictional scratch outline, create the collection from the editor and power bar, change it by mouse/key/`act`, edit a field, watch it update in both clients, then undo; include one script calculated value and one relation query. If distributed as an extension, install and uninstall it through the extensions screen in that same scratch journey. The spike is one experience and one reviewable PR, not a ladder of validation PRs. [Repository verification](../../../../CONTRIBUTING.md#verification), [extension install rule](../extensions/README.md#testing-an-extension).

The Datacore lesson is the **object/query/view split with live identity**. The opportunity is the missing authoring and editing experience around it. ep0ch already has a service query, script producer, view primitives, autocomplete hooks, one reader/editor and action registry; the accepted collections capability should connect those parts until one person can actually use a collection all day.

### Working spike in this branch

This branch closes a concrete seam in that design: an installable read handler can declare a Question in its manifest, bind it to the saved view note, receive the service's full `blocks.query` answer as `input.query`, and rerun when `QueryWatches` says that answer changed. The Collection workbench extension then draws one saved view as linked table, cards and a selectable, previewable, filterable list through the shared primitives and NoteSurface. Its component schema exposes the source, properties and example to completion, `ep0ch library` and agent tools. A scratch outline proved installation by mouse and `act`, source edits changing the answer, and uninstall with ordinary notes and the saved view retained.

A local scratch-host latency probe on float-box changed 80 matching notes over three seconds while a second client pinged the host. With the workbench uninstalled, ping p95/max were 2.9/3.8 ms; installed and rendering the 80-row answer, they were 2.9/3.5 ms. This measures one live view on a small fictional outline, not pie's full 11k-note workload. Each write calls `QueryWatches.changed`; a burst settles into a watched re-evaluation, and an answer change starts one read handler process for that view. No bulk records are written by the extension.

The accepted Collections capability remains the owner of the final tabs, direct controls and write-back cells. This spike makes the service-to-extension path and the daily reading/agent journey tangible without inventing another query language or collection index; it does not claim that its three simultaneous presentations are the final four-tab collection UI.
