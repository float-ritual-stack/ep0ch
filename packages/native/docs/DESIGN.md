# Native ep0ch: one catalogue, one layout, one dispatcher

**Base:** interaction-first (hands first, `TileCx`, `App::person`, `one_owner.rs`, per-tile memo). **Grafted:** grammar-first's saved-tree shape, one list over `site.answer` and the forkability check; service-first's `ActionRow`, served validation, shipped screens as one extension and `PRIMS` by primitive type.

**The claim, bounded.** A new screen, or a tile over an existing source, is a note. A new list source is one host producer, written once for every client. A new drawer is Rust, and there are four.

**Basis.** The maps and judges, plus spot reads of `desk/layout.ts:1036-1045`, `desk/tiles.ts`, `desk/screen-specs.ts`, `surface/keymap.ts` and the Waiting manifest. W0, W1, W2, the first hydra sweep, W3, W4, the second hydra sweep, W5, W6, W7, the third hydra sweep, F1 (a quote as drawn), F2 (a caret that opens something), F3 (ways out), W8 (the terminal), H1 (typing), H2 (arranging by mouse), H3 (small things from the first run by hand), H4 (a comment in place), RW (the wire review's fixes), R0 (the Rune pin moved to `a5360a6`), K1 (keys everywhere) and K2 (what opens where) are built: [PROBES.md](PROBES.md) has what the probes found, and where this page says more than the code does, the line says "not built yet".

## 1. Primitives

| Primitive | Owns | Describes itself as |
|---|---|---|
| **Store** | every read, watch, re-ask, stale `last()`, the 64-slot budget; one `Link` per outline and machine. As built (W7): the links, slots and keys are a hub the windows of a run share, and a `Store` is one window's face on it (what it wants, the answers as it last took them, what is its to hear) | the `Ask`; `peek` lists slots, their tiles (another window's named with its window) and `n/64` a link |
| **Action** | every state change; the dispatcher checks the actor against `touches` and records the step | `ActionRow` in outline-core: `id, summary, args, touches, keys, while, menu, examples, answer` |
| **Key table** | chord to act line, per whereabouts layer | rows `{chord, line, layer, from}` (`from`: `row`, or `screen` for the open screen's own) |
| **Layout** | arrangement, focus, wires, policy, floats, folds; `place` | the door's saved tree; `Landing {tile, why}` |
| **Kind row** | what a tile kind is: a drawer, a source, its fields | the `extensions.list` `tileKinds` row, carried on `screens.list` as `kinds`: `{kind, name, about, drawer \| render \| view \| command, fields, replaces}` |
| **Drawer** | drawing one answer shape: `page`, `list`, `view` (since W7, over `tiles.view`), `pty` (since W8: a program's grid, `tiles/pty.rs`) | `{id, about, notes, lists, takesKeys}`; `facts` is what `peek` says of its tile |
| **Program** (W8) | what runs in a terminal tile (`pty.rs`, no Rune): its grid, how it stands, the ways in. `Programs` is the run's registry, in the store's hub; a `Host` opens, lists and ends them (the terminal's crates behind the `pty` feature, a scripted one for scenes, none in a build without) | `pty::Shown`: `{key, name, command, backend, keeps, attached, stands, report}`; `said` is what `lists.read from=programs` is handed |
| **Primitive registry** | one `El` builder per primitive type the service answers (`tiles/prim.rs`) | `{type, describe, fills}`, held to `outline-core/fixtures/primitives.json` |
| **Draft** | one session for whatever is written in a tile (`draft.rs`): its text, the revision it stands on, what it writes (`Writes`: a block's own text, a comment on a note, a reply in a thread), its hold on the service (a block's only), the file that keeps it; held by the App, shown by the tile it is written in. Not built yet: a card's draft, and a draft shown in a float | `peek`'s `editing`: `{note, writes, on, revision, unsaved, text, caret, held, hold, said, completing}` |
| **Screen** | a named layout with keys, lands, menu | `ScreenSpec` as `screens.list` answers it, with `problems` |
| **Anchor** (H4) | a place on drawn text that other things attach to: a part of a page (by the line of its note it starts on) and a range of the text its view is drawn from (none: the part whole). The service finds it (outline-core's `part-anchor.ts`, through `drawn-passage.ts`'s `spanIn`) and says it on the part (`PagePart.marks`); `parts.rs` reads it (`Anchor`, `Mark`, no Rune); the one builder of prose tints the range and the page drawer puts the thing beside it. A comment thread's passage is the first thing attached; a proposal's passage, a range somebody just wrote and a card that hovers over words attach the same way (a `kind`, an id, the act a press runs, the list whose row is the thing) | `peek`'s `marks` on a reader: `{kind, id, part, range, act, from, whole, says}` |

```rust
// store.rs
struct Ask { at: OutlineAt, action: String, params: Value, watch: bool }  // equal asks share one slot
struct Store { links: HashMap<OutlineAt, Box<dyn Link>>, slots: HashMap<AskKey, Slot<Value>>, users: HashMap<AskKey, HashSet<TileId>> }
// actions/mod.rs: the row is data; `run` is Rust. A line is read into a Request; one already read (a script's call,
// a row's pick, the control socket's) goes to act_request and is never written as a line to be read again
impl App { fn act(&mut self, line: &str, by: Actor) -> Outcome; fn act_request(&mut self, req: Request, by: Actor) -> Outcome }
// layout.rs: no Rune, no socket
enum Node { Leaf(TileSpec), Split{dir, weights, kids}, Tabs{active, kids}, Columns{kids}, Flow{anchor, kids}, Dock{side, open, kid} }
// (as built: who acts, how they stand, where the person is and what each tile is are `Ctx`; an open is told the tile it may make)
fn apply(l: &Layout, op: &Op, ctx: &Ctx) -> Result<Applied, Refusal>;   // Applied { layout, changed, answer }
// (as built, F3: a refusal is data, outline-core's way-out.ts: why not, and each way out as an act; no key, no sentence with an action in it)
struct Refusal { reason: String, ways: Vec<Way> }
struct Way { act: String, args: Vec<(String, Value)>, tile: Option<String>, does: String, at: Option<String>, on: Option<String>, then: bool, theirs: bool }
fn place(l: &Layout, req: &Request, sprout: &TileSpec, ctx: &Ctx) -> Landing;
// actions/mod.rs: what an act is about when it names no tile; App::target finds the tile, once an act
enum About { Nothing, Any, Notes, Lists, Tree, Drafts, Placed }
struct Action { row: &'static ActionRow, run: fn(&mut App, &Args, &Actor) -> Outcome, about: About }
// tiles/mod.rs
struct Drawer { id: &'static str, about: &'static str, notes: bool, lists: bool, asks: fn(&TileCx) -> Vec<(&'static str, Ask)>, draw: fn(&TileCx, &Kit) -> El, facts: fn(&TileCx) -> Value, takes_keys: bool, version: fn(&TileCx) -> u64 }
// tiles/prim.rs (it builds `El`s, so it sits inside the renderer seam; `parts.rs` is its Rune-free model)
struct Prim { ty: &'static str, describe: &'static str, fills: bool, build: fn(&Value, &PrimCx, &Kit) -> El }
static PRIMS: &[Prim];
// draft.rs: no Rune; the field's text is the seam's own type
enum Writes { Block, Comment { on: Option<Quoted> }, Reply { thread: String, to: String } }  // Quoted: the words, how they were read, and where the service found them
struct DraftSession { tile: Id, note: String, writes: Writes, revision: u64, base: String, buf: keys::Text, hold: Hold, told: Option<Told>, completing: Completing }
// parts.rs (H4): no Rune; the range is UTF-16 offsets of the part's `view.text`, as the service says it
struct Anchor { part: u64, range: Option<(usize, usize)> }
struct Mark { at: Anchor, kind: String, id: String, act: Option<String>, from: Option<String> }
fn map_cursor(offset: usize, spans: &[Placed]) -> usize;  // outline-core's mapCursor, held by core-contract.json
```

`TileCx` hands a drawer the store (read-only), its `TileSpec`, its kind's row, its `TileUi` and one way out, `cx.act(line)`: an act line run from its tile (a row's own, a button's, an action of this window's; `App::act_from` says whether it is about that tile). No `&mut Layout`, no socket, and no line written for a row: what a pick runs is the `act` the service wrote. `Node` reads both of the door's saved forms (`ratio, a, b` and `weights, kids`) and saves `kids`.

Not primitives: an Attachment (it is a follower tile), a presets folder, a figure-name registry. The terminal is the `pty` drawer; what runs its programs is behind a cargo feature (`pty`, off by default: the drawer and the model are always built, and draw a scripted host's programs in a scene).

## 2. A screen is a note

A `[type::screen]` note in the outline: two bodies, one spec. The door's JSON fence stays. New: child blocks, where nesting is the tree and properties are the door's flat `TileSpec` fields. `screens.list` lowers both to one validated `ScreenSpec`; `screen.save` writes the block form.

```text
Garden work [type::screen] [screen::garden-work] [lands::reader] [focus::beds]
- split row [ratio::0.3]
  - tile query [name::beds] [query::type=bed NOT stage=done] [select::reader]
  - tabs
    - tile reader [name::reader]
    - tile backlinks [name::links] [source::tile:reader] [subject::follows]
- keys
  - ctrl+l [action::bar.open source=query]
```

Lowered, in the door's saved shape:

```json
{"name":"garden-work","lands":"reader","keys":[{"key":"ctrl+l","action":"bar.open","args":{"source":"query"}}],
 "layout":{"focus":"beds","root":{"t":"split","dir":"row","weights":[0.3,0.7],"kids":[
  {"t":"leaf","kind":"query","name":"beds","query":"type=bed NOT stage=done","wires":[{"verb":"select","to":"reader"}]},
  {"t":"tabs","active":0,"tabs":[{"t":"leaf","kind":"reader","name":"reader"},
   {"t":"leaf","kind":"backlinks","name":"links","source":"tile:reader","subject":"follows"}]}]}}}
```

As built in W2 (outline-core's `screen-note.ts`, which holds the whole form): a key is named as the door names keys
(`ctrl+l`; `readSpec` refuses `mod+l`), a tab set saves its tiles under `tabs`, and what a property can't hold (a list,
an object, a typed argument) is the block's own ```json fence. `screens.save` is the one writer of the form.

- **Shipped screens and kinds:** `screens[]` and `tiles[]` of one extension, `packages/outliner/extensions/screens/` (on wherever the service runs), served by `extensions.list` and read through the same `screens.list` (bb: core uses the path it exposes). As built (W3): native compiles in no screen and no kind (`scripts/native-forkable` holds that), and opens on the screen whose spec says `start`. The door's literals for the navigator, last callers and who's online are deleted; its kinds' descriptions are the rows'. Left in the door: it holds those three screens from the extension's manifest file until a host serves them (and keeps them when the extension is uninstalled), and `desk` and `board` are still screens it makes from its own state (named layouts, a hub's views), so each of those two names is two screens, one a door.
- **Kinds:** extension tile rows already come in three shapes, each bound to a drawer with no client code: `render` to `view`, `view` query to `list`, `command` to `pty` (as built in W8: `screens.list` serves a `run` tile with `drawer: pty` and the line that starts it, its folder and its machine as fields; the terminal extension's Shell and Agent are two such rows, the agent's command its row's field). One new field, `drawer`, names a client-drawn kind (`page`, `list`), and `fields` what a tile of it starts with (a list's `from`). `screens.list` serves each tile's kind already resolved (a retired name, a name an extension's kind `replaces`), with what a retired name said as the tile's fields (outline-core's `canonLeaf`: a `pinned`, and a `detail` that names a page, are readers with `mode: pinned`), and the name its screen wrote as its `role`, so no client maps old names and `tile=role:reader` names the same tile in both doors. As built (sweep 2): a new-note rule's `only` and `unless` are resolved the same way, and a kind's row says which of the names it `replaces` it serves now (`serves`: one kind a name, the last to take it). A tile made in the window is written by the name screens write (`KindRow::written`) and found through `serves`; the layout's rules know every kind by that name (`App::known_as`), as a policy's `accepts` is written. The asker says which drawers it has; a kind served for one it hasn't is said on the tile.
- **The live arrangement:** a state file per outline, `native-<outline>.layout.json` beside the control socket, as the door keeps `desk.json`. No machinery note until the door moves too. As built (W7): a window that switches outline keeps each outline's file, and the one it left parked in memory as it stood; a window torn from another keeps no arrangement, on the outline it was torn on or on one it switches to, only what is written in it (`native-<outline>.<window>.drafts.json`, which the next run's first window on that outline brings back).
- **The kitchen** (W7): `kitchen` is a screen of the screens extension, so both doors list it: tiles and a toolbar that show the parts each wave added. Today it holds W7's: the extensions and the outlines as list tiles, the bar on each, a tile torn out; and W8's: the programs as a list tile, and buttons that open a shell, an agent and the bar on the programs.

## 3. Service and client

**Outline-core gains** (pure moves, merged to main early): `screen-spec.ts` (types, validator, tile address), `screen-note.ts` (block-form lowering), `action-row.ts` (the door's `ActionDef extends ActionRow`) and `fixtures/` (`layout-contract`, `act-lines`, `action-rows`, `screens`).

**Wire, one PROTOCOL bump at the final rebase:**
- `screens.list` (watched): notes and extension screens, validated, addresses resolved, `problems[]`. The door's `screen-notes.ts` switches to it.
- `lists.read` (watched, a module of its own: `list-producers.ts`), `from:` a producer: `children`, `search`, `query`, `lanes`, `facets`, `links`, `properties`, `activity`, `clients`, `screens`, and `sources` (the producers as rows). Each answers a `ListAnswer` around a `ListPrimitive`: rows with `chips`, the `act` line a pick runs, and for a tree `depth`, `folds`, `open` (`arrange: tree` joined `list-row.ts`); `open` says which folders are answered. `sources` answers each source as it says of itself (`ListSource`: its parameters, whether a bar lists it, whether its answer carries facets), which is what a client reads. `links` reads a note's groups as a page's `::links` does (`readLinks`): the groups, their labels and "every group when none is named" are outline-core's `link-blocks`. As built it is its own action, not a `site.answer` producer: `site.answer` is bound to a note, and a tree or a search has none. As built (W6, `about-producers.ts` beside the table): `threads`, `proposals`, `revisions` (a note's, by `of`), `actions` (the asker's own action rows, handed over as `actions`, answered as the ways to press them, the keys of the screen the asker names first: any door's keys screen) and `components` (every component schema; an open one carries its example lowered through the page's own walk). A row may show something under itself (`ListRow.view`, a page primitive), a press of its own inside a row is a cell with its `act`, and `open` names the rows that are open in any list whose rows fold, not only a tree's folders. A change between two texts is a `diff` primitive (`note-page.ts`), found by the service (`text-diff.ts`). As built (W8, `list-programs.ts`): `programs`, the programs a door runs in its terminal tiles, handed over by the asker as `actions` is (`programs`: each as it says of itself) and written as rows whose pick is the jump (`terminal.jump key=`). The truth is on the asker's machine (herdr-core there, or a pty of the window's own), which may not be the service's, so the service keeps no registry and no `sessions` producer was built. What the asker's keeper runs that the asker did not start is listed with no pick.
- `notes.page`: its row says `watch: "later"` (a module answers it over a turn and keeps the watch) and it is in `WATCHABLE_ACTIONS`, as `screens.list` is. As built in W4: a part is `{type: "part", kind, block, span, line, …, view}`: the note it is written in, its UTF-16 span in that note's text, its first line, the service's word on its answer, and the primitive to draw. A figure is the catalogue primitives outline-core's `figure-primitive.ts` lowers its answered props to (a kind with no form: the service's Markdown, else its lines as `source`); a button is a `button` with the line a press names it by, and the slots its line leaves empty as `needs` (what stops a press: any other word the service has on a button, a look it doesn't read, is said and stops none, as in the door); a box holds the parts written inside it. Every press in a part carries the act line it runs (`act`, stamped by outline-core's `withActs` with the one rule, `actOf`: a list's row, a card, a text, a table's row and cell), a row is keyed by the note it opens, and the notes under the note are the one list too (`under`). Which component a line starts is one function, outline-core's `componentAt`, asked by the published page, `notes.page` and the door's reader. A comment on the note and an edit proposed beside it are blocks under it and no notes of it (outline-core's `isNoteUnder`, one answer for the tree, the page and a links list): `children` and `under` leave them out, as the published page does, and `lists.read from=threads|proposals` has them (W6, sweep 3). Not built yet: an extension's component and a `::use`'s body as primitives (both are `source`); script parts cached by script, props and deps.
- `completion.rows` takes `{text, cursor}` in place of a detected `target` (W5, `outliner/src/completion-at.ts`): the host runs `completionTargetAtCursor`, asks its sources as for any client, merges with `mergeSourceAnswers` and answers `{token, rows, heading, message, pickKey}`: the token to replace (UTF-16 offsets of the text) and rows ready to draw and to write (`insert`, `select`, `pick`). What the list says of itself is outline-core's `completionSaid`, which the door's completer calls too; whether Return is the field's while a row is lit is outline-core's `enterKeeps`, said on the row (`enter`). Not built yet: a row that makes something when chosen (a page nobody wrote, an anchor on a heading, a new component) is left out of this form, and the door's own sources (its actions, a fence's settings, a button's steps) have no thin form.
- `completion.rows` says what a row is (H1): each row of the text-and-cursor form carries its source's own words (`docs`, `SourceRow.docs`), and the row the asker says is lit (`lit`, the first unless said) what choosing it makes (`view`): its source's `example` as written and lowered through the page's own walk (`drawnExample` in `note-page.ts`, the builder the library's rows use). One row's, never every row's: an example is a note walked, with the questions it asks. The order is the target form's (`mergeSourceAnswers` with the outline's picks: what the notes carry, most used first, then what the components give a meaning; a test holds the two forms equal).
- `draft.patch` for a holder that places nothing (W5, `outliner/src/draft-place.ts`; PROBES §10): a new ask kind, `place`, beside `read`, `patch` and `revert`. Asked to `patch`, the native window answers with its draft as it stands; the service decides with outline-core's `placeDraftPatch` (the door's guard, moved there, and still what the door runs over its own buffer) and sends back the spans to replace, taken only while the text is the version they were found in. No hold flag and no client kind: the holder says it by what it answers.
- `lists.read from=query|lanes` answers every level of a group (RW): `group` names one property or two (`stage,crop`, as `blocks.query` takes it), and a group's own groups come with it (`ListGroup.groups`), each named by the way to it and a missing value labelled by its own level's key, as a view of the same question lists them (`site-producers.ts`). `listSections` and its port already drew such groups (`core-contract.json`'s `sections`); the producer had dropped the second level.
- `lists.read` gains two sources a bar lists (W7, `outliner/src/list-extensions.ts`): `extensions` (a row a thing to do with one: open its page, its settings, install one, and once words are typed remove one, each with its act line) and `outlines` (`outlines.known`: this machine's outlines and each forwarded machine's own list, answered by the host through `outline-links.ts`; it opens and makes none).
- `tiles.view` (W7, watched as `notes.page` is; `outliner/src/tile-view.ts`): what a tile of a kind an extension's script renders shows, as one view primitive with every press said as its act line (`withActs`). `screens.list` says the drawer for such a kind (`view`), and `list` over its question for a kind that lists a query, so neither needs client code. An extension's settings reach the scripts it ships as props (`settingProps`), each its default when unset: a setting changes what a rendered tile draws in every client.
- `passages.find` (H4, `outliner/src/passage-find.ts`): where a quoted passage is in a note's text, asked before anything is written about it, by the comment's own lookup (`blockCommentSelection`): `{start, end, exact, quote, widened}` or the refusal a comment on it would get. With `whole: words` a passage that starts or ends inside a word takes the whole word (outline-core's `wholePassage`), and `quote` is what to send in the asker's place. Asked with the part the words end in as the asker drew it (`part`: its span of the note and the text its view is drawn from), it also answers `at`, the range of that text the passage is (`spanIn`, as a page's marks are found): a run of prose is one part however long, and what is written about words in it stands at them. A read, unwatched.
- `notes.page` marks (H4): a part says what is attached to its drawn words (`marks`: `{kind, id, start, end, act, from}`): each current thread whose passage reaches into it, as a range of the text its view is drawn from (a prose part's Markdown), the act a press runs (`thread.toggle`, the door's name) and the list whose row is the thing (`threads`). A part drawn from more than words is marked whole; a box's own parts carry theirs. A thread resolved or whose words are gone marks nothing.
- `events.subscribe` takes client kind `native` (W4): the window registers as itself and hears `scripts.act` and `scripts.ended`, so an act a script has for a window reaches its dispatcher and is answered (`scripts.answer`). Not built yet: `door.act` aimed at a native window.

**Client-side:** layout, ops, placement, focus, the key table, cursor and scroll, the draft buffer, drawing, picture decode, cells, windows, the arrangement file, the control socket.

## 4. One owner each

| Decision | Owner |
|---|---|
| Who acts, and whether | `rule()` in `actions/mod.rs`, the one check `App::act` makes: the actor and how they stand against what the row declares (`touches`, `while`, and `person` for what is the person's own). An agent's `touches: screen` act waits while the person types, and until they have been idle 2 s (`Whereabouts.idle`). What an agent may do to the arrangement (`touches: shape`) is the layout's own rule, asked by `reshape` with the same standing. Held to the door's `actorRule` by `actor-contract.json`: both dispatchers answer every row alike (whether, not in which words) |
| How an agent stands on the person's press | `App::stands`: the person, or the run of a button they pressed while its acts carry the invitation that press minted (`actions/script.rs`, the door's `surface/invite.ts`: one run's, spent when the run ends). `rule()` reads it, the layout is told it (`App::asked`), and an action that does something only for the person asks it. A script's act always runs as the script (`Actor::Agent`): who the service says asked for a run is never read |
| Who a write is recorded as | `Store::write` stamps `mutation.actorId` from the actor of the act: a script's write is the script's, on the person's press too |
| Which tile has focus | `Layout.focus`, changed only in `apply`: by `Op::Focus`, by what a load leaves, and by the layout's own steps when a tile takes the keys or the tile with them goes (an open's new tile, a close, a replace, a take, a group or its spill, a move, a float, a dock slid shut, a tab, a zoom, a fill, a flow's travel), each the door's rule by contract. An agent's step is refused when it would take the tile with the person's keys or move them while they type; the one way it moves them is by shutting the dock they are in (`dock.toggle`, which waits until they are idle), when they go to the first tile shown. `keys::follow`, in `poll`, is the one reconciler and the only caller of `Tx::focus`: a press inside a tile becomes `tile.focus`, and the tile the layout names is the one Rune focuses. Each tile's root holds the keys through `keys::tile` |
| Who has the keys | `App::person() -> Whereabouts`: the bar while it is open, else the tile `Layout.focus` names, in its draft when a block is being written there, in that draft's completion list while it is open (a layer over the draft's: `Layer::stack`; one with nothing to choose from keeps only the key that puts it away). Which of those layers a block's keys are in is `App::writing`, which the hint row under its field reads too. As built (W8): in its program when that tile is a terminal's (`App::in_program`: its drawer takes the keys, its program runs, and the person has not stepped out with `tile.leave`): the layer is `program`, `takes_keys` and `busy` are true and `typing_in` names the tile, so the actor rule holds an agent's act for that tile back as it does for a draft. Every key but the layer's own rows is sent to the program, and the rows that hold everywhere are not asked there. (A float joins when it is built) |
| What keeps a program, and for how long | the host that opened it says (`Opened.backend`, `keeps`, `attached`); `pty::kept_said` words it once, for the tile and for the list's row. Whether a program was found running or started is asked of what keeps it when it is opened, never remembered. What it keeps is asked off the frame (the first read, an open, an end, the host's own thread): `Host::listed` is what it last said |
| How a program stands by its own word | the program (OSC 7501), as its host passes it on (`pty::Report`, from herdr-core's list). No screen is read for one |
