Kitchen sink

Every part the docs site is built from, drawn here with the door's own colours. Use this page when you write or change a page. The door's kitchen sink, ep0ch --showcase, is where each feature's recording comes from.

Information architecture

One shell, two jobs. Showcase shows what the door does, one page per showcase section. Build teaches how to add to it. Since the app is moving to a small kernel with features as configuration and extensions, Build is half the site. Reference and Concepts serve both.

Colour roles

Pages ask for a role, never a colour. bun site/tokens.ts writes every role from the door's calm theme, and again from night. Try the switch in the status bar: everything here changes with it. There is no light theme, and nothing is ever pure white.

Type and spacing

The door is set in cells, so the site is too wherever it speaks for the door: headings, chrome, code, keys and stills use one monospace. Prose uses a face built for legibility, at a 68-character measure. The scale is a minor third from a 17px body.

Code and terminal surfaces

Two wells, told apart by what's in them. A code well (sunk, with a file label) holds text you copy. A terminal well (the ground, framed) holds what the door drew, cell for cell, from ep0ch show --ansi or a cast frame. Never put a screenshot where a still can go: a still is text, it follows the theme, and it can be searched.

Cast player with chapters

Purpose: show a feature working, in the door, as a recording the reader can pause, scrub and jump through by chapter. It leads every feature page.

head
what it shows, who drives it, its length and chapter count
screen
asciinema-player (self-hosted) on a .cast; before it loads, the first frame as text, so the page is complete at rest
chapters
the cast's own m markers, one per tour step; a click seeks and plays; the current one is selected as the door selects
foot
its keys, and where it was recorded: section, size, theme

Do

  • Record a showcase section through a tour, in cells mode.
  • Name chapters by what happens: "Change a type: callout.type".
  • Keep it under a minute and eight chapters.
  • Say on screen when an agent acts, as the door does.

Don't

  • Use a GIF or a video: it can't be paused, scrubbed or searched.
  • Record a real outline, or stage a demo outside the showcase.
  • Autoplay, or loop.
  • Name chapters "Step 3".

Do

  • One command a block, so each can be run on its own.
  • Use made-up notes: an allotment, a kitchen, a bike shed.
  • Find notes by an exact property (--query "menu=sunday"), never by words that might match others.

Don't

  • Elide with ... anything a reader would copy.
  • Put a $ prompt or output in the copied text.
  • Leave a placeholder like <id> where a command can find it.

Keybinding chip, and the three ways

Purpose: name how to do something, in all three ways the door takes it. Mouse and agents are first-class, so an action documented by key alone is half-documented.

Keys: ⏎ f ctrlz ^W v. Mouse: a callout's title. Agent: callout.type n=2 to=danger.

ToKeysMouseAgent
Fold or open one( ) then fits titlefold.toggle text=collapse
key chip
one key a chip; a chord is chips side by side; the door's own names (⏎, ^W, ctrl)
mouse chip
dashed: the thing you click, not "click here"
act chip
the action and its arguments exactly as ep0ch act takes them

Do

  • Give every action a row with keys, mouse and act; write "none" where a way doesn't exist.
  • Copy keys from ep0ch actions, so they match the door.

Don't

  • Write "Cmd" or "Ctrl" in prose; use the chip.
  • Document a key the door doesn't bind on that screen.

Callout set

Purpose: set apart the few lines a reader mustn't miss. The site uses the door's own callouts: the same types, icons and tones, framed the same way.

✎ Folding never writesnote

A fold lives in the reader. The note's text changes only when you choose "start folded".

✦ Keep the showcase open beside this pagetip

Every feature page names its section; ep0ch --showcase opens it live.

⚠ Icons are one columnwarning

An emoji draws two columns wide and breaks the frame, so it's refused.

△ This writes to the outline your folder namesdanger

Run it in a folder whose .ep0ch names a scratch outline.

? Why not a light theme?faq

The door is dark, and so are its readers' eyes at 2am. The site is the door's, so it's dark too, with a dimmer night theme.

❝ From the ticketquote

Animated GIFs are out: they can't be scrubbed or paused, and the useful part comes late in the loop.

title row
icon, title, and the type's name at the end, as the door draws it
body
one to three sentences; a foldable one is a <details>
tone
from the type, never chosen per page

Do

  • Use warning and danger only for real risk.
  • Keep it short; put background in the prose.
  • Fold technical evidence ([!note]-).

Don't

  • Stack two callouts with nothing between them.
  • Use a callout as a heading, or for the lede.
  • Invent a tone; there are six.

API signature block

Purpose: one action, method or type at a glance: how to call it, what it touches, what each argument means, where it lives. It's generated from ep0ch actions and outline-core's types, so it can't drift.

callout.start n=<number>? line=<number>? folded=<boolean>

Makes a callout start folded (folded=true writes [!type]-) or open (folded=false writes [!type]+): the one change to the text that folding ever makes.

Don't

  • Document an internal helper as API.

Content rules

  • Headings go two deep. The page's title, its sections (h2), and at most one level inside (h3). Something that wants an h4 is a second page.
  • One idea a section. If its heading needs "and", split it.
  • A guide goes concept, example, reference. One short concept section that names the parts. Then the example as steps that run. Then what changes it. Then the full reference.
  • Show, then tell. A feature page leads with its cast. Prose explains only what the cast can't: why, the grammar, the edge cases.
  • Every action, three ways: keys, mouse, act.
  • The glossary's words: block, tile, container, screen. "Pane" is Herdr's or tmux's box.
  • Made-up notes in every example, cast and still. Never a real outline.
  • Link, don't direct. Not "see below", but a link to the section.
  • Plain sentences, from the reader's side: "the type choice opens", not "the ListPicker is instantiated".
