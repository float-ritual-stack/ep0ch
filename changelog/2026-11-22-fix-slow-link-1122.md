### The slow-link frame tests were red when the clock turned its minute inside one, not when the box was busy (PIE-1817, PIE-1808)

- **The reds:** `test/session.test.ts`, "a slow link gets the latest frame, never a queue of old ones (PIE-1163)", a different test each night, green alone both times. Nov 17: "two answers truly lost cost one stale wait…" had `unacked: 1` for 0 (`frames: 22`, `bytes: 3220`). Nov 22: "a reader that stops answering while 200 frames are made…" had `skipped: 200` for 199 (`frames: 2`, `bytes: 1476`).
- **The cause:** these tests count frames one by one, and their door was a whole one: its 33 ms tick repaints the status row when the clock's minute turns. A turn inside a test's wait was one frame the test never made: skipped when the window was full, sent and unanswered when it was open.
- **Not the door's pacing:** both nights `ackTimeouts` was what the test expected (0, then 1), so nothing was judged stale or lost by a stretched wait. A status row is a frame like any other on a slow link, and the window treated it as one.
- **Not the load:** the unchanged block beside eight busy loops in a 200% slot was green 20 of 20. With every test started 100 ms before the minute it was red every time: the same two tests, the same numbers as the nights' logs to the byte, the tick's reason `clock: "10:36" -> "10:37"`.
- **A second frame nobody made, found under load:** a terminal of another size attaching starts a resize, and 500 ms later the door draws again for where it ended. That landed inside four other tests of the block (one of them in 16 of the 20 loaded runs), which don't count it; in the first test it would be `skipped: 200` again, on a box slow enough to hold it 300 ms between attaching and waiting.
- **The fix, in the tests:** the block's `counting()` session lets go of what its door draws by itself (the tick, the frame after a resize ends), so every frame counted is one the test made. No assertion changed. A new test holds it: with the clock a minute on and a resize ended, 100 ms later nothing was sent or skipped (red with the tick left running: 4 messages for 3).
- **Runs after:** started 100 ms before the minute, 17 of 17 green with no frame of the door's own in any test; beside eight busy loops in a 200% slot, 10 of 10 runs green; `session.test.ts` and ten frame, paint, link and session neighbours each alone, green.
- **No merge to bisect:** the tick's clock is older than the tests, so each has had this since it was written (Oct 25 for PIE-1163's, Nov 2 for PIE-1500's). A red needs the minute to turn inside a few tenths of a second of waiting, which is why it came twice in a week of nights and never alone.
- **Seen, not changed:** the real-socket test "a client whose terminal stopped answering…" reads `unacked: 0` a moment after its last answer from a real session with a real clock; a minute turning in that tenth of a second would be the same red. It hasn't been seen.
- **Run:** nothing; no PROTOCOL, GRAMMAR or schema change. The budget file is untouched.
