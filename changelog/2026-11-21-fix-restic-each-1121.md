### backup-restic's red in the nightly's each-file phase was a 2 s wait that restic outlasts on a busy box (PIE-1816)

- **The test and the assertion:** "every rollback point of an old log restores from the snapshot that let it go" (`test/backup-restic.test.ts`), `expect(at(point.seq).txn).toBe(at(point.seq + 1).txn)`: red on Nov 18 and Nov 21, only with eight files at once.
- **The cause:** the test wants a rollback point inside a log transaction that runs on into the next write. It got one by accident: the host writes its record of the extensions' pages outside any store transaction, which leaves the log's transaction open. Note routing ends it: 2 s after a note is made it reads its rules in a store transaction. A restic upload sits between the point and the test's next write, so the point was inside a transaction only when restic was done within those 2 s.
- **Not the backup's:** no shared path and no restic lock was in it; the fixture repository (#1521) and the held chains (#1522) are as they were. The backup restores such a point either way; only the test's setup depended on the timing.
- **The fix, in the tests:** `leaveLogTransactionOpen` (the door's `test/scratch.ts`) makes the open transaction on purpose, with note routing off for that outline, so nothing ends it however long restic takes. backup-relay's "a rollback point the laptop uploaded itself" had the same assertion and the same red, and uses it too.
- **A second race, backup-relay's:** a host writes its extensions' pages to an outline a moment after it opens it (about 90 log entries). Beside seven other files the job read the log before they landed, and "unchanged: nothing is sent again" relayed `garden` a second time. `writeNotes` (`test/scratch.ts`) writes through the host and answers once those writes are in (`settled`, the host's word for it); backup-restic, backup-relay and backup-status use it, and backup-status's poll for a log that stopped moving goes.
- **The each-file phase names the test:** `scripts/test-each.sh` keeps, under a red file's `✗` line and indented, each failing test's error, what it expected and got, where, and its `(fail)` line (8 lines a test, 5 tests a file), or that no test failed and bun's exit code (a file that didn't load, or stopped at its 900 s). `scripts/nightly-red` reads a night's log (the red files; with `--tests`, what failed in each), and `scripts/nightly-main` puts that in the ticket as "Failing tests".
- **Runs, beside eight busy loops in a 200% slot:** before, backup-restic red 4 of 4 (the same test and line each time) and backup-relay red 3 of 3. With only `writeNotes` added, backup-restic was still red 2 of 5 and its rollback test by itself 8 of 8, which is what named the 2 s wait. After: the rollback test green 8 of 8, backup-restic 5 of 5, backup-relay 5 of 5. Each alone: green, as on main.
- **Seen, not changed:** the pages' record is the one write the host makes outside a store transaction that this found (`extension-pages.ts`), and a store transaction that only reads ends an open log transaction. Neither loses anything; both are why a rollback point can sit inside a transaction at all.
- **Run:** nothing; no PROTOCOL, GRAMMAR or schema change. The budget file is untouched.
